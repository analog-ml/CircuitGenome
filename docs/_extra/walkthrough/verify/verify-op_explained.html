Part 1 · Why this file exists

The one job: the metric benches ask how well does this amplify. Before that question means anything, something has to ask is this circuit even switched on.

Gain is a small-signal quantity. Small-signal quantities are computed about an operating point. If the operating point does not exist, everything downstream is fiction.

A transistor amplifies only in saturation, carrying real current. Stack too many devices between the rails at a low supply and some of them end up in triode — or off entirely. The circuit still simulates. The AC sweep still returns numbers. They just describe a linearisation around a point the circuit never occupies.

So this file runs a DC .op, reads every device's actual operating point, and turns that into a verdict:

sized circuit → .op → (sound, reason)

It has two consumers with different appetites. The designer uses check_bias_soundness() as a gate — a candidate that cannot bias is rejected before anyone looks at its gain. The AC bench uses _bias_diagnostic() as an explanation — when a sweep finds no gain, this says which devices were in triode and hints at the usual cause.

Part 2 · Reading every device's operating point

The one job: get id, vds and vdsat out of ngspice, for every transistor, by name.

Unlike the metric benches — which dump numeric columns with wrdata — this one asks ngspice to print named values and then parses its stdout:

probe = "".join(
    f"print {pre}[id]\nprint {pre}[vds]\nprint {pre}[vdsat]\n"
    for pre in prefixes.values()
)

Those prefixes are the reason deck.py's _dev_prefix() exists. On PTM or generic, a device answers to @m.xdut.m1_load. On a foundry PDK it is a subcircuit, so the BSIM4 device sits one level deeper — @m.xdut.x1_load.m0 for GF180, or under a per-cell handle for sky130.

Get that path wrong and nothing errors. ngspice prints nothing for the unknown handle, the regex matches nothing, and the file concludes the simulation failed. The bias verdict for an entire PDK silently becomes "sim-failed". That is a lot of weight on one string.

Single-ended: bias it in unity feedback

The SE reader biases the circuit through the same Lfb/Cfb loop the gain bench uses, and auto-detects polarity the same way — whichever assignment settles. That matters: the operating point being read should be the one the measurements happen at, not some other DC state.

Part 3 · The fully-differential verdict — and a bench that lied

The one job: decide whether an FD circuit has a usable output state, without the measurement rig inventing one for it.

Fully-differential circuits get their own reader, and its history is instructive. The original one tied the outputs back to the inputs to establish a DC state. Two things were wrong with that:

  • Against a real CMFB loop the tie network is bistable. At tight headroom ngspice converges on its degenerate all-off solution, and perfectly healthy circuits were condemned.
  • The ties force outp == outn, which makes the obvious sanity check — "did the outputs split apart?" — impossible to fail. The check existed and could never fire.

The current reader anchors the inputs and vcm_ref at Vcm with no feedback ties, matching the DC state the FD metric benches actually run in. With the outputs free, two questions become answerable:

FD skips the per-device checks, deliberately

Having read every device's operating point, the FD path then declines to judge them individually. The reason is specific: with the inputs at Vcm, the CMFB amplifier's tail — whose own inputs also sit at Vcm — and the main tail run in marginal triode by design at low supplies. Degraded, still functional, and universal to the family.

Condemning on that would reject every low-voltage CMFB variant, including ones that measurably amplify at this very operating point. A genuinely dead FD circuit rails or splits its outputs instead — which the verdict above already catches — and the metric benches quantify whatever marginality remains.

Part 4 · _op_bias_problems() — two ways to be wrong

The one job: from a dict of operating points, name the devices that are not doing their job.

for ref, d in op.items():
    ida = abs(d.get("id", 0.0))
    if ida < 1e-7:                                # starved: effectively off
        starved.append(ref)
    elif abs(d["vds"]) < abs(d["vdsat"]) - 1e-3:  # triode: not saturated
        triode.append(ref)

Starved means below 0.1 µA — the device is off, so whatever it was meant to do (mirror a current, provide a load) is not happening.

Triode means |Vds| < |Vdsat|: the device is on but has not been given enough drain-source voltage to saturate. A current source in triode is not a current source; a gain device in triode has collapsed output resistance. The 1 mV margin keeps a device sitting exactly at the saturation edge from flickering into the list on numerical noise.

The elif matters: a starved device is reported as starved, not additionally as triode. One diagnosis per device, and the more fundamental one wins.

Part 5 · check_bias_soundness() — condemn only on evidence

The one job: return (sound, reason), and be very careful about ever returning False.

This is a gate. The designer rejects candidates on its verdict, so a false condemnation quietly deletes a working design from the search — and nobody ever sees the one that got away. The whole function is written around that asymmetry:

if not ngspice_available():
    return True, None       # cannot check → do not condemn

No simulator means no evidence, and no evidence means no conviction. The function can only ever downgrade a verdict that something else already reached; it never upgrades one, and it never guesses.

The three ways it does condemn, each on positive evidence:

EvidenceVerdict
the .op railed (SE: at both polarities; FD: an output at a rail, or split)no usable mid-rail bias
ngspice crashed or never convergedno operating point to assess
SE only: devices starved or in triodebias not established, with the refs named

Each reason string names up to four offending devices, with an ellipsis beyond that — enough to debug from, short enough to print in a results table.

The same machinery, used to explain rather than judge

_bias_diagnostic() reuses the reader for the AC bench. When a sweep finds no gain, the interesting question is not "is this sound" — it plainly isn't — but why. It returns a one-liner naming the triode and starved devices and floating the usual cause: stacked devices that do not fit the supply headroom. It is wrapped in a bare except, because a diagnostic that fails must never take down the measurement it was trying to explain.

Part 6 · What it honestly does not do

  • It checks one operating point — nominal corner, inputs at CM. A circuit that biases here and falls over at ss passes.
  • It does not check the bias is good, only that it exists. A device scraping into saturation by a millivolt is "sound" here; the metric benches are what quantify the consequences.
  • FD circuits get an output-state verdict only. Per-device condemnation is switched off for them on purpose, so an FD circuit with genuinely starved internals but healthy outputs passes this gate.
  • Every threshold is a constant: 0.1 µA, the 0.1–0.9·Vdd window, 0.2·Vdd of output split. They are calibrated for the shipped topologies, not derived from anything.
  • Without ngspice it always answers "sound". Silence is not a pass.

In one sentence: op.py runs one DC operating point and reads every transistor's id, vds and vdsat out of it, so a circuit that never establishes a usable bias can be rejected before anyone takes its gain seriously — condemning only on positive evidence, and staying silent when it has none.
