The one question: how do we measure how well a fully-differential op-amp ignores noise, when a perfect simulation says it ignores all of it?

The PR's pieces, as a call graph. Each box is one Part below; the analog background comes first, and the function that ties everything together comes last.

Part 1 · Why this exists

The one job: if someone wiggles the inputs together, or wiggles the power supply, how much of that wiggle leaks into the op-amp's output?

An op-amp is supposed to amplify only the difference between its two inputs. Any input signal splits into two parts:

  • differential: vdm = in+ − in−, the signal we want;
  • common mode: vcm = (in+ + in−)/2, what both inputs share, usually noise or interference.

Two scores say how well the amplifier ignores what it should ignore:

CMRR = Adm / Acm      PSRR+ = Adm / Avdd

Acm is the gain from a common-mode wiggle to the output; Avdd is the gain from ripple on the positive supply. Both are quoted in dB (20·log10): 60 dB is 1 000×, and real op-amps typically reach 60–100 dB. Remember that range.

Two boats on the tide

A single-ended (SE) op-amp has one output, measured against ground. A fully-differential (FD) op-amp is two mirror-image halves, and its output is the difference between its two output wires. Picture two boats tied side by side: the tide (common mode) lifts both equally, so their height difference never changes.

perfectly matched halves ⇒ Acm = 0 ⇒ CMRR = ∞

So what did the old bench print?

The SPICE deck builds the two halves from identical transistors, so the true answer is exactly zero. But a computer subtracts two large, nearly equal floating-point numbers:

v(outp) = 1.650000000000123 V
v(outn) = 1.650000000000122 V
──────────────────────────────
difference ≈ 1e-12 V              ← rounding error, not the circuit

Dividing a real gain by that rounding error gives absurd rejection. A gf180 FD circuit with 77.6 dB of gain, traced by hand:

A_dm ≈ 7 600
A_cm ≈ 1e-12
CMRR = 7 600 / 1e-12 = 7.6e15  →  20·log10 ≈ 318 dB

That is the 260–315 dB the old bench reported across a gf180 sample. It was measuring the precision of the calculator.

Why it was a real bug

The designer accepts candidates by comparing SPICE numbers to the spec. With cmrr_min_db = 60, 318 dB passes, so every FD circuit passed every CMRR and PSRR spec. Occasionally the noise landed under the bench's 1e-12 “nothing measured” cutoff, and that circuit was rejected as unverified: pass or fail was partly luck. The existing test only checked gain < cmrr < 400, and 318 fits inside that window.

In one sentence: matched FD halves cancel every common-mode and supply wiggle exactly, so the old bench divided by floating-point rounding error and called it rejection.

Part 2 · Mismatch

The one job: if two transistors are drawn identically, how different do they actually come out, and how much CMRR does that difference cost?

Manufacturing works at the scale of atoms. The dopant atoms under each gate land at random, gate edges are rough, the oxide thickness varies by fractions of a nanometre. So every transistor's threshold voltage Vth comes out a little different. Two bakers following one cookie recipe never get the same number of chocolate chips.

Global vs local: the distinction that matters

How big? Pelgrom's rule

A big gate covers many dopant atoms, so the randomness averages out, like flipping 10 000 coins instead of 10. Pelgrom (1989) measured it:

σ(ΔVth) = AVt / √(W·L)

It is written line for line in the gf180 nmos_3p3 wrapper:

+ par_vth=0.007148                                   ← A_Vt = 7.148 mV·µm
+ p_sqrtarea='sqrt((par_leff)*(par_weff))'           ← √(W·L)
+ var_vth='0.7071*par_vth* 1e-06 / p_sqrtarea'       ← Pelgrom, per device
+ mis_vth=agauss(0,var_vth,1)                        ← the random draw
m0 d g s b nmos_3p3 ... delvto='mis_vth*sw_stat_mismatch'

The 0.7071 is 1/√2: Pelgrom's AVt describes the difference between two devices, and a difference of two independent draws spreads √2 more than one. And sw_stat_mismatch is 0 by default, the off switch this PR turns on.

Traced by hand for w=2u l=0.5u:

Leff = 0.5 − 0.15 = 0.35 µm      Weff = 2.0 + 0.10 = 2.10 µm
√(W·L) = √0.735 ≈ 0.857 µm
σ(Vth)  = 0.7071 × 7.148 / 0.857 ≈ 5.9 mV   (one device)
σ(ΔVth) = 7.148 / 0.857          ≈ 8.3 mV   (a pair)

In ngspice, two such “identical” transistors with mismatch on drew 29.9 µA vs 28.5 µA, 4.8% apart, which is what a few mV of ΔVth at this bias predicts.

How mismatch makes FD CMRR finite

CMRRFD ≈ 2·gmRSS × gm/Δgm
topology:  gm = 200 µS, R_SS = 1 MΩ  →  2·gm·R_SS = 400   →  52 dB
mismatch:  Δgm/gm = 5 %              →  gm/Δgm   = 20    →  26 dB
CMRR ≈ 400 × 20 = 8 000                                   →  78 dB
Δgm = 0                              →  CMRR = ∞          (Part 1's dead end)

The sizer's analytical formula, gm1/(2·gd,tail) = gmRSS/2, is the topology factor only, the single-ended view. So for FD designs, analytical and SPICE now measure different things (e.g. 40.6 vs 71.4 dB on one gf180 circuit), and that gap is the missing gm/Δgm, not a model bug.

PSRR follows the same story. With a PMOS input pair the tail hangs from VDD, so supply ripple looks to the pair just like a common-mode input. That is why PMOS-input designs read CMRR ≈ PSRR (36.2 / 35.9 dB on one sky130 circuit).

Mismatch is random, so one simulation describes one imaginary chip. The bench simulates 8 and reports the worst (Part 7).

In one sentence: Pelgrom's random, 1/√(W·L)-sized mismatch is the only thing that lets common mode and supply leak into an FD output, so it must be in the simulation for CMRR and PSRR to mean anything.

Part 3 · Turning mismatch on: _emit_model()

The one job: tell ngspice “give every transistor its own random imperfection, and the same imperfections every time”.

Both foundry PDKs already ship the mismatch physics, switched off. The switch names differ, so each tech's YAML records its own:

PDKSwitchWhere the PDK sets it to 0
gf180sw_stat_mismatchdesign.ngspice, the .include before the .lib
sky130mc_mm_switchinside each corner section of sky130.lib.spice
ptm45 / genericnoneno mismatch model
 
# tech_gf180mcu.yaml → spice_lib:
  mismatch_switch: sw_stat_mismatch     # new SpiceLib field; None when absent
def _emit_model(tech, corner=None, mismatch_seed=None) -> str:
    if mismatch_seed is not None and not (
            tech.spice_lib and tech.spice_lib.mismatch_switch):
        raise ValueError(f"{tech.name} has no mismatch model")
    if tech.spice_lib:
        lib = tech.spice_lib
        out = f'.include "{lib.design}"\n' if lib.design else ""
        out += f'.lib "{lib.file}" {corner or lib.corner}\n'
        if mismatch_seed is not None:
            out += (f".param {lib.mismatch_switch}=1\n"
                    f".option seed={mismatch_seed}\n")
        return out
  • The guard refuses mismatch on PTM. Without it, the PTM branch would silently ignore the seed and return a perfectly matched deck, which is the original bug again.
  • .param <switch>=1 redefines the switch; when ngspice sees a .param twice, the later one wins, so every delvto = mis_vth × 1 becomes a real random shift.
  • .option seed=K fixes the random sequence: a deck of cards shuffled with seed 3 always comes out in the same order.

Why the line order matters (sky130)

Proof, from raw ngspice

The switch turns mismatch on, the same seed gives the same chip, a new seed gives a new chip. And critically, the two devices differ: the random draw lives inside each transistor's subcircuit, so every instance rolls its own dice. One shared draw for the whole circuit would be a global shift, a corner, and would keep the symmetry.

one random draw per transistor, not one per circuit

simulate_metrics then builds 8 imperfect copies of the same sized design: [_dut(tech, name, body, corner, mismatch_seed=s) for s in _MISMATCH_SEEDS].

In one sentence: two lines appended after the PDK's .lib turn its built-in per-transistor mismatch on and fix the seed, and the guard makes sure a tech without mismatch models can never quietly measure a perfect circuit.

Part 4 · The new problem: offset rails the output

The one job: once the halves are unequal, where does an open-loop FD op-amp's output actually sit, and can we measure anything there?

Mismatch gives the amplifier an input offset Vos: the small input difference needed to balance the output, like a bathroom scale reading 0.4 kg with nobody on it. It is a few millivolts. The CMRR bench runs the op-amp open-loop, and open-loop gain multiplies those millivolts:

A_dm = 77.6 dB ≈ 7 600×      Vos = 5 mV
v_out = 7 600 × 5 mV = 38 V     ← on a 3.3 V supply: clipped at a rail

Turning mismatch on with the old rig, the DC differential output for 5 seeds was −3.19, +3.24, +3.22, +3.18, +3.25 V (gf180) where healthy is “a few mV”. At a rail, transistors sit in triode or off. AC analysis linearises around that broken operating point, so the gains describe a broken amplifier: testing a car's acceleration while it is parked against a wall. Worse, the railed rig printed believable numbers (110–118 dB on gf180, 39–64 dB on sky130), so nothing would warn you.

“Doesn't the CMFB keep the outputs centred?”

The CMFB controls the average of the outputs, not their difference.

Before this PR the open-loop rig was fine only because perfect symmetry made Vos = 0. The FD gain bench (_loop_fb) still holds the inputs at Vcm through 1 GΩ resistors with nothing fed back. The single-ended bench never had this problem: its huge inductor Lfb is a wire at DC (feedback cancels the offset) and an open circuit at the measurement frequency (open-loop gain). That is exactly what the FD bench needs.

OptionVerdict
Close a normal feedback loop (e.g. gain −1)measures closed-loop gain; CMRR needs open-loop Adm
Apply −Vos by handunknown in advance; different for every seed
Bring back the pre-#165 cross tiesbistable against a real CMFB; latches
DC-only differential feedback (a servo)finds −Vos itself and is invisible to the AC measurement

In one sentence: a few millivolts of mismatch offset times huge open-loop gain pins the differential output to the rails, which the CMFB never notices, so the bench needs feedback that cancels the offset at DC but vanishes at the measurement frequency.

Part 5 · The DC servo: _fd_servo_fb()

The one job: automatically find and apply the −Vos that balances the output, without the correction touching the AC measurement.

Think of balancing a tray on one finger while someone taps it to measure its wobble. A fast hand cancels the taps too; no hand lets the tray slide off. A very slow hand corrects only the slow drift and never notices the taps.

_SERVO_CLAMP_V = 0.05   # per-input limit on the FD offset servo's correction

def _fd_servo_fb(vcm, sign: int) -> str:
    lim = _SERVO_CLAMP_V
    corr = f"max(min({sign}*v(lp)/2,{lim}),-{lim})"
    return (f"Vocm ocm 0 {vcm}\nVci ci 0 dc 0\nVdi di 0 dc 0 ac 1\n"
            "Esrv vsrv 0 outp outn 1\nRsrv vsrv lp 1\nCsrv lp 0 1e12\n"
            f"Binp inp 0 v={vcm}+v(ci)+v(di)/2-{corr}\n"
            f"Binn inn 0 v={vcm}+v(ci)-v(di)/2+{corr}\n")

The B-sources separate the two worlds

Add and subtract the two formulas (ignoring the clamp):

inp − inn     = v(di) − 2·corr      ← differential: stimulus knob + servo
(inp + inn)/2 = vcm + v(ci)         ← common mode: stimulus knob only

The servo can only ever move the difference, never the common mode whose leakage we are measuring.

Trace the DC loop

At DC the capacitor is open, so v(lp) = vout and inp − inn = −sign·vout. With the offset battery:

vout = A·(−vout + Vos) ⇒ vout = A/(1+A)·Vos ≈ Vos
A = 7 600, Vos = 5 mV
v_out     = 7 600/7 601 × 5 mV = 4.9993 mV   (instead of railing at 3.3 V)
inp − inn = −4.9993 mV                    (the servo found −Vos by itself)

The leftover output is the offset, which is why nulled outputs sat at 4–16 mV on gf180 and up to 33 mV on sky130.

Trace the AC measurement

“32 000 years” costs no simulation time: op solves the after-infinite-time state directly (capacitor open), and AC analysis solves the steady 1 mHz response directly.

The clamp: why ±50 mV

The first, unclamped prototype latched on several seeds:

With the clamp, all 30 prototype draws (3 circuits × 5 seeds, both PDKs) nulled. A draw whose offset exceeded 100 mV would saturate the clamp, rail, and be rejected by the DC check (Part 7): an honest “cannot measure”.

The sign: why both directions are tried

Negative feedback must oppose the imbalance, and which way that is depends on which input is non-inverting. The AC bench's FD polarity is only a hint (the two assignments differ only in sign), so the caller tries both. On a gf180 NMOS-pair circuit, sign +1 railed 4 of 5 seeds and sign −1 nulled all 5. When the wrong sign happened to null (ngspice found the unstable balance, a pencil on its tip), it gave the same CMRR, 56.2 dB. The AC reading depends only on the operating point, so the rule is simply: accept whichever sign nulls the output.

In one sentence: _fd_servo_fb feeds the differential output back through a 10¹² s filter, cancelling the mismatch offset at DC while staying blind at 1 mHz, and its ±50 mV clamp keeps it from shoving the inputs into a latch.

Part 6 · One draw, one run: _fd_draw()

The one job: for one mismatched chip, is the output balanced, and if so, what are its differential, common-mode and supply gains?

AC analysis is linear: several AC sources at once would add up and be impossible to separate. So, like testing which of three taps leaks by opening one at a time, the control script moves a single 1 V AC stimulus between knobs:

op
let vchk=v(outp)-v(outn)
print vchk                       ← did the servo null it?
ac lin 1 1e-3 1e-3               ← one point at 1 mHz, Vdi carries the AC
let adm=mag(v(outp)-v(outn))
print adm
alter vdi acmag=0
alter vci acmag=1                 ← move the stimulus to the common mode
ac lin 1 1e-3 1e-3
let acm=mag(v(outp)-v(outn))
print acm
alter vci acmag=0
alter vsup acmag=1               ← …then onto VDD
ac lin 1 1e-3 1e-3
let avdd=mag(v(outp)-v(outn))
print avdd

Why 1 mHz? It is below even a sub-hertz dominant pole, so it reads the full low-frequency gain; it matches the first point of the main gain bench; and it is ten decades above the servo's corner.

def _fd_draw(name, ports, body_dut, vdd, ibias, cl, vcm, netmap,
             sign) -> dict[str, float] | None:
    deck = _deck(name, ports, body_dut, vdd, ibias, cl,
                 _fd_servo_fb(vcm, sign), netmap, _FD_REJECTION_CONTROL)
    txt = _run_capture(deck)
    if not txt:
        return None
    vals = dict(re.findall(r"^(vchk|adm|acm|avdd)\s*=\s*([-\d.eE+]+)", txt,
                           re.M))
    if len(vals) < 4:
        return None
    return {k: float(v) for k, v in vals.items()}
  • _run_capture + print, not wrdata: each ac creates a new result plot (ac1, ac2, ac3), and one wrdata cannot easily mix them. op.py already parses print output with a regex.
  • Distinct let names label each reading so the regex can find it.
  • All or nothing: if the operating point fails, ngspice stops early and lines are missing; the draw is None, never half-measured.
  • _fd_draw only reports vchk; judging it is the caller's job (Part 7).

One real sky130 draw, by hand

adm  = 2 032.22      →  66.16 dB   (nominal gain 66.4 dB: healthy point)

Why one run

Every ngspice launch re-reads the PDK library. The first version used 4 runs per draw (32+ per circuit) and took 15.7 s on sky130; one run per draw takes 4.4 s, about 3.5× faster, with numbers identical to all 7 printed digits (seed 1: adm 2.032220e+03, acm 2.710371e+01, avdd 2.787803e+01 both ways).

In one sentence: one ngspice run per chip checks the DC output, then moves a single 1 V stimulus from the differential knob to the common mode to VDD with alter, so all three gains come from the same operating point.

Part 7 · Putting it together

The one job: given 8 imaginary chips of one design, what single CMRR and PSRR should we report, and which designs get this treatment at all?

_MISMATCH_SEEDS = tuple(range(1, 9))

def _measure_fd_rejection(name, ports, mc_bodies, topo, vdd, ibias, cl, vcm,
                          polarity):
    if polarity is None:
        return None, None
    netmap = _fb_netmap(topo, *polarity)
    cmrr, psrr = [], []
    signs = (1, -1)
    for body in mc_bodies:
        for sign in signs:
            r = _fd_draw(name, ports, body, vdd, ibias, cl, vcm, netmap, sign)
            if r is not None and abs(r["vchk"]) < 0.05 * vdd:
                break
        else:   # neither servo direction nulled this draw
            continue
        signs = (sign, -sign)   # the direction is the circuit's, not the draw's
        for out, key in ((cmrr, "acm"), (psrr, "avdd")):
            if r["adm"] > 0 and r[key] > 1e-12:   # numerical zero → not measured
                out.append(20.0 * np.log10(r["adm"] / r[key]))
    return (min(cmrr) if cmrr else None, min(psrr) if psrr else None)
  • “Nulled” means |vchk| < 0.05·VDD (165 mV on gf180, 90 mV on sky130). A nulled draw sits at the offset (0.3–33 mV); a railed one near VDD (1.8–3.3 V), so the limit separates them cleanly.
  • for … else: the else runs only if the loop ended without break, i.e. neither sign worked, and continue skips that chip.
  • Remembering the sign: the right direction depends on the wiring, not on millivolts of mismatch, so after chip 1 every chip tries it first, typically 9 runs instead of up to 16.
  • The 1e-12 guard: a leak that reads as numerical zero is “not measured”, never “infinite rejection”, so Part 1's trap cannot return.

The hidden equation

The code never writes it, but the PR is a small Monte Carlo worst-case estimator of Part 2's textbook result:

CMRRreported = mink=1..8 20·log10(Adm,k/Acm,k),   CMRRk ≈ 2gmRSS·gm/Δgm,k

If the leak is roughly Gaussian across chips, the largest of 8 draws typically lands about 1.7σ out (P(all 8 below x) = 0.5 gives x ≈ 1.7σ), so “worst of 8” is roughly a 1.5–2σ worst case, conservative but not the 3σ of production sign-off.

Open question: the sky130 folded cascode

Folded-cascode designs on sky130 read only 13–15 dB of CMRR against 87.6 dB of gain and a 78.7 dB analytical estimate. The result repeats across draws, the gain under mismatch stays within 1–2 dB of nominal, and the offset is nulled. The working hypothesis: the CMFB corrects both load currents by the same amount, mismatched load devices take it unequally, and the folded cascode's enormous output resistance turns that small current difference into a large differential output. If so, it is real physics (high-impedance FD outputs are known to be sensitive to CMFB mismatch), but it has not yet been checked by enabling mismatch in the CMFB devices alone.
